# Голос в каналах через SFU (LiveKit)

Зачем: голосовые каналы шли сырым PCM 16 кГц по WebSocket (TCP). Отсюда «металлический» голос (16 кГц режет
тембр), треск при любой задержке сети или alt-tab в игру (TCP ждёт потерянный пакет, звук рвётся) и эхо у тех,
кто без наушников (звук через Web Audio не попадает в эхоподавление Chrome). С SFU голос идёт Opus 48 кГц по
UDP через WebRTC: встроенный джиттер-буфер и сокрытие потерь Chromium, эхоподавление работает, канал — десятки
кбит/с вместо 256.

## Как устроено

```text
 браузер / ПК-приложение / Android                     VPS (docker compose)
 ┌──────────────────────────────┐   /ws (JSON)        ┌──────────────────┐
 │ lib/voice.ts  «кто где»      │ ──────────────────► │ vicinity (Drogon)│  voice_join / voice_state /
 │                              │   GET /rtc/sfu      │  выдаёт токен    │  voice_speaking — как раньше
 │ lib/sfu.ts    сам звук       │ ◄────────────────── │  комнаты (JWT)   │
 │   mic → RNNoise → gain ─┐    │                     └──────────────────┘
 │   Room.connect(token)   │    │   wss://host/livekit/rtc (nginx → livekit:7880)
 │   publishTrack(Opus) ◄──┘    │ ──────────────────► ┌──────────────────┐
 │   remote tracks → <audio>    │   UDP 7882 (TCP 7881)│ livekit (SFU)    │  комната voice-<channelId>
 └──────────────────────────────┘ ◄─────────────────► └──────────────────┘
```

- **Сервер Vicinity остаётся источником правды** о том, кто в каком канале: `voice_join`, `voice_state`,
  `voice_speaking`, `voice_media`, «Слушать вместе», активности — всё по `/ws`, как в docs/API.md §11.
  LiveKit несёт только медиа. Поэтому старые клиенты (Qt-десктоп) по-прежнему видят участников, а оверлей
  и индикаторы работают без изменений.
- **Вход.** `GET /api/v1/rtc/sfu?channel_id=N` → `{url, room, token, identity}`. Те же правила, что у
  `voice_join`: голосовой канал сервера, где состоишь (текстовый — 400), или личка/беседа, где участник
  (403 посторонним, 404 нет канала). Лимит — как у `voice_join`. Токен — JWT HS256 с грантом LiveKit
  (`roomJoin`, `room: voice-<N>`, `canPublish`, `canSubscribe`, без `canPublishData`), `sub: u<user_id>`,
  `name: display_name`, срок 2 часа (`backend/utils/Sfu.cc`). **SFU не настроен — 404**, и клиент
  идёт старым путём.
- **Клиент** (`web/src/lib/sfu.ts`, выбор в `web/src/lib/voice.ts`): при входе в первый канал пробует
  `/rtc/sfu`; 404, нет ответа за 8 с или ошибка подключения — старый движок (PCM через WebSocket). SFU
  пропал посреди разговора (`Disconnected` не по нашей воле) — выходит и входит заново: новый токен, а
  если SFU не поднялся — PCM. Переход в другой канал — другая комната.
- **Микрофон** проходит ту же обработку, что в старом движке и в звонках: RNNoise и усиление в одном
  AudioContext 48 кГц (`openMic(…, {inline: true})`), встроенное шумоподавление браузера при RNNoise
  выключено. Публикуется одна дорожка Opus (`AudioPresets.speech`, DTX, RED). Рация — усиление 0, пока
  клавиша не зажата (без сигналинга на каждое нажатие). Мут/«не слышать» — `mute()` публикации и
  громкость 0 у всех участников.
- **Индикатор «говорит».** Свой — по `ActiveSpeakersChanged` от SFU (в рации — по клавише); дальше как
  раньше уходит `voice_speaking` в `/ws`, чтобы видели старые клиенты и оверлей. Чужие — по SFU для
  участников комнаты; по `/ws` для тех, кто говорит PCM.
- **Громкость и устройство вывода**: `RemoteParticipant.setVolume` (0…2, через Web Audio) и
  `room.switchActiveDevice('audiooutput')`.
- **ICE.** Клиент передаёт в комнату те же STUN/TURN, что и звонкам (`GET /rtc/ice`, coturn с временными
  учётками) — за симметричным NAT медиа пойдёт через TURN.

## Развёртывание

`deploy/.env`: `LIVEKIT_API_KEY` (`openssl rand -hex 8`) и `LIVEKIT_API_SECRET` (`openssl rand -hex 32`, не
короче 32 символов; сервер отказывается от короткого). Ключи читают и контейнер `livekit`, и `vicinity`.
Снаружи нужны **UDP 7882** и TCP 7881 (панель хостера, ufw). Сигналинг идёт через сайт: nginx проксирует
`/livekit/` → `livekit:7880` (`deploy/nginx.conf`), поэтому ни домена, ни сертификата у LiveKit нет.
**Сценарий Б** (nginx хоста перед контейнерами): в его конфиге нужен `location /livekit/` с заголовками
`Upgrade`/`Connection`, как у `/ws` — готовый блок в `deploy/host-proxy/nginx-vicinity.conf`. Без него
WebSocket не открывается, и клиент молча идёт по старому пути. Caddy пропускает WebSocket сам.
Конфиг — шаблон `deploy/livekit.yaml`, в который при старте контейнера подставляются `PUBLIC_IP` и ключи
(секрет не попадает в командную строку). Без ключей контейнер просто ждёт, `/rtc/sfu` отвечает 404 —
голос работает по-старому.

Проверка: `curl -s https://ДОМЕН/livekit/` → `OK`; в журнале `vicinity-server` строка
«Голос через SFU: LiveKit /livekit»; в браузере `window.__vicinityVoiceStats.sfu === true` после входа
в канал.

## Ограничения и что дальше

- **Смешанные каналы.** Qt-десктоп (`client/`) умеет только PCM через `/ws`: в одном канале с теми, кто
  через SFU, он их не слышит и они его тоже. Список участников и индикаторы при этом общие. Решение —
  либо LiveKit-клиент в Qt, либо списать Qt-клиент в пользу ПК-приложения (Electron), которое и так
  основное.
- **Камера и показ экрана** в каналах пока идут старым путём — прямыми соединениями между браузерами
  (`lib/voiceVideo.ts`, до 8 зрителей). Следующий шаг — публиковать их в ту же комнату с simulcast: один
  исходящий поток на любое число зрителей, 5 стримов на канал и 50 зрителей без нагрузки на отправителя.
- **Сквозное шифрование** комнаты: LiveKit поддерживает E2EE (insertable streams), ключ комнаты надо
  раздавать участникам через сервер Vicinity. Не сделано.
- **E2E-тесты** идут против бэкенда с «мёртвым» адресом SFU (`web/e2e/start-backend.mjs`): токены
  проверяет `a3-sfu.spec.ts`, тесты голоса идут по старому пути через откат. Живой SFU в CI не поднимается.
